# 판정

`docs/plan.md`의 4단계("판정")를 처리한다. 이 티켓의 마지막 단계다 — 통과하면 **이 스킬이 커밋까지
수행한다.** 코드를 새로 고치는 단계가 아니다 — 문제를 발견하면 스스로 고치지 않고 멈춰서 보고한다
(고치는 일은 3단계, `.claude/skills/implementation/SKILL.md`의 몫이다).

## 멈추는 조건

이 스킬이 완료 기준에 도달하지 못한 채 멈추려 하면, 왜 멈추는지 아래 3가지 중 하나로 스스로
판단해 `docs/rotations.md`에 한 줄 남긴다(질문을 던지고 답을 받아 같은 실행 안에서 계속
이어간다면 남기지 않는다):

- **회색지대**: 판단이 필요한 지점이라 AskUserQuestion으로 묻고 멈춘다.
- **맴돌다 끊김**: 같은 원인으로 제자리걸음이라고 스스로 판단되면 멈추고 사람을 부른다 —
  테스트가 실패했다는 사실 자체는 이유가 아니다(TDD 특성상 정상적인 실패일 수 있다).
- **예산 소진**: 컨텍스트/턴 예산이 바닥나 완료 기준에 도달하지 못하고 멈춘다.

## 0. 입력 확인

**먼저 확인**: 이 스킬이 이미 서브에이전트로 실행 중인지 확인한다(예: `ticket` 오케스트레이터가
Agent 도구로 이 스킬 호출을 위임한 경우). 이미 서브에이전트라면 바로 아래 절차를 이어서 진행한다.
그렇지 않고 사용자가 이 스킬을 지금 세션에서 직접 호출한 경우라면, 코드를 작성한 세션이 스스로
판정하면 자기 검증 편향이 생기므로 여기서 멈춘다 — Agent 도구로 새 서브에이전트(`general-purpose`,
`run_in_background: false`로 포그라운드)를 하나 띄우고, 그 서브에이전트에게 티켓 ID를 주며 "Skill
도구로 `verdict` 스킬을 호출해 이 SKILL.md 절차(0단계부터)를 처음부터 그대로 따르라"고 지시한다.
그 서브에이전트가 반환한 결과(마무리 보고 내용, 커밋 해시)를 그대로 넘겨받아 사용자에게 전달하고,
이 세션은 직접 1~5단계를 수행하지 않는다.

아래 명령으로 `.claude/gate/state.json`에 이 스킬이 시작됐음을 기록한다 — Stop 훅이 이 스킬이
끝나는 시점에 테스트를 실제로 돌렸는지, 완료 못 하고 멈췄다면 `docs/rotations.md`에 기록을
남겼는지 확인하는 데 쓴다:

```bash
mkdir -p .claude/gate && jq -n --arg s "verdict" --argjson rb "$(wc -l < docs/rotations.md | tr -d ' ')" '{current_skill:$s, completed:false, tests_verified:false, rotations_baseline:$rb}' > .claude/gate/state.json
```

인자로 티켓 ID(`T-n`)를 받는다.

- `git status`, `git diff`로 지금 작업 트리에 커밋 안 된 변경이 있는지 확인한다. `src/main/java`
  변경이 없으면 3단계(구현)가 아직 안 끝난 것이다 — 안내하고 멈춘다.
- 이 티켓의 인수 테스트를 실행해 통과하는지 먼저 확인한다. 실패하면 3단계가 안 끝난 것이니 안내하고
  멈춘다.

## 1. 컨텍스트 로드

- `docs/principles.md`, `docs/plan.md`를 읽는다.
- `docs/acceptance-criteria.md`에서 대상 `# T-n 인수 조건` 블록 전체를 읽는다.
- `git diff`로 이번 티켓에서 바뀐 파일 목록과 변경 내용을 전부 읽는다.

## 2. 바뀐 코드를 요구사항과 대조

- `git diff`의 각 변경이 대상 규칙 블록의 `When → Then` 예시가 요구하는 동작과 일치하는지 확인한다.
- 최소 변경 원칙이 지켜졌는지 확인한다 — 요구사항과 무관한 리팩터링, 새 추상화가 섞여 있으면
  짚어서 사용자에게 알린다.
- 이 과정에서 `acceptance-criteria.md`에 없는 규칙(코드가 침묵하던 정책, 예상 못 한 분기)을
  만나면, **사양인지 버그인지 스스로 판단하지 않는다.** `docs/tickets.md`에 새 티켓으로 남길지
  검토한다(형식은 `docs/plan.md`의 "새 티켓 남기기"를 따른다).

## 3. 완료 기준

이번 티켓의 인수 테스트가 통과하고, 쌓은 테스트가 전부 통과하면 완료다 — 요구사항대로
됐고(2단계) 원래 되던 것이 안 깨졌는지(이 단계) 둘 다 확인돼야 다음(커밋)으로 넘어간다.

- 2단계에서 짚은 요구사항 불일치나 중복 지점 누락이 없어야 완료다 — 하나라도 남아 있으면
  여기서 멈추고 사용자에게 알린다.
- 전체 스위트를 돌린다 — 실행 명령은 `docs/plan.md`의 "이 저장소의 실행 방법"을 따른다.
- 전체 스위트를 실행했으면(결과와 무관하게) 아래 명령으로 실제로 돌렸다는 사실을
  `.claude/gate/state.json`에 기록한다:
  ```bash
  jq '.tests_verified=true' .claude/gate/state.json > .claude/gate/state.json.tmp && mv .claude/gate/state.json.tmp .claude/gate/state.json
  ```
- 결과를 못 읽으면 완료로 치지 않고 멈춘다(`docs/principles.md` "확인이 안 되면 통과가 아니다").
- **명령 출력에서 결과 요약 줄(`BUILD SUCCESSFUL`/`BUILD FAILED`, `n tests completed, m failed` 등)과
  실패 테스트가 있다면 그 클래스/메서드명을 그대로 옮겨 적어 둔다 — 이 인용은 6단계 보고에 그대로
  쓴다.** "모두 통과했다/일부 실패했다"처럼 결과 줄을 인용하지 않고 서술로만 판정하지 않는다.
- 이번 티켓의 인수 테스트가 통과하고, 그 외 기존 테스트가 전부 그대로 통과해야(회귀 없음) 완료다.
  진짜로 완료됐으면 아래 명령으로 `completed`를 표시한다:
  ```bash
  jq '.completed=true' .claude/gate/state.json > .claude/gate/state.json.tmp && mv .claude/gate/state.json.tmp .claude/gate/state.json
  ```
- 실패가 있으면 완료가 아니다 — 이 스킬은 스스로 코드를 고치지 않는다. 어떤 테스트가 왜 깨졌는지,
  방금 옮겨 적은 실패 테스트명을 근거로 정리해 사용자에게 보고하고 멈춘다. 3단계로 돌아가 고친
  뒤 다시 이 스킬을 실행해야 한다.
- 참고: `./gradlew test`는 매 실행마다 `build/reports/tests/test/index.html`(사람이 읽는 HTML
  리포트)과 `build/test-results/test/*.xml`을 새로 남긴다. 세션이 끝난 뒤에도 사람이 직접 열어
  대조할 수 있는 근거이므로, 6단계 보고에 이 경로를 함께 적는다.

## 4. `docs/tickets.md` 최종 확인

- 2단계에서 남기기로 한 새 티켓이 있으면 추가한다. `docs/plan.md`의 "새 티켓 남기기" 형식을
  지켰는지 확인한다.
- 이번 티켓 처리 중 이미 열려 있던 관련 항목(질문, 후속 티켓)이 이 작업으로 해소됐으면, 남겨둘지
  정리할지 사용자에게 확인한다 — 조용히 지우지 않는다.

## 5. 커밋

전체 테스트가 통과했을 때만 진행한다.

- `git status`로 이번 티켓과 무관한 변경이 섞여 있지 않은지 확인한다. 섞여 있으면 관련 파일만
  골라 스테이징한다(`git add -A` 금지).
- 커밋 메시지는 이 저장소의 관례(`git log` 최근 커밋 참고, `type: 한글 설명` 형태)를 따른다.
  본문에는 무엇을 바꿨는지가 아니라 왜(요구사항/버그) 바꿨는지를 적는다.
- 원격에 push하지 않는다 — 이 스킬의 범위는 로컬 커밋까지다.

## 6. 마무리 보고

- 요구사항 대조 결과(2단계)는 요약해도 되지만, **전체 테스트 결과는 3단계에서 옮겨 적은 결과 요약
  줄과(실패가 있었다면) 실패 테스트명을 그대로 인용한다.** "테스트가 모두 통과했습니다"처럼 실행
  로그 인용 없이 지어낸 문장으로 대신하지 않는다.
- 3단계에서 확인한 HTML/XML 테스트 리포트 경로(`build/reports/tests/test/index.html` 등)를 함께
  적어, 사용자가 이 보고를 믿지 않고도 직접 열어 확인할 수 있게 한다.
- 커밋 해시와 포함된 파일 목록을 보고한다.
- 새로 남긴 티켓이 있으면 번호와 제목을 함께 보고한다.
