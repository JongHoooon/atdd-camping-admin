# 구현

`docs/plan.md`의 3단계("구현")를 처리한다. 이 스킬은 **3단계까지만** 담당한다.
판정(4단계, 전체 회귀 확인과 커밋)에는 관여하지 않는다 — 전체 테스트 스위트를 돌리거나 커밋하지 않는다.

## 멈추는 조건

- 같은 실패가 세 번 반복되면 멈추고 사람을 부른다
- 한 바퀴 돌 때마다 무엇을 했는지 `docs/rotations.md`에 한 줄 남긴다

## 0. 입력 확인

인자로 티켓 ID(`T-n`)를 받는다.

- 이 티켓에 대응하는 실패하는 인수 테스트가 이미 있는지 테스트 소스 루트에서 확인한다(Javadoc의
`T-n:` 표기로 검색). 없으면 2단계(`.claude/skills/acceptance-test/SKILL.md`)가 아직 안 끝난
것이다. 먼저 그 스킬을 실행하라고 안내하고 멈춘다.
- 대상 테스트 클래스만 실행해(명령은 `docs/plan.md`의 "이 저장소의 실행 방법" 중 "특정 테스트
클래스만 실행"을 따른다) 지금 실제로 실패하는지 확인한다. 이미 통과한다면 고칠 대상이 아니다 —
어떤 메서드를 다룰지 다시 확인한다.

## 1. 컨텍스트 로드

- `docs/principles.md`, `docs/plan.md`를 읽는다.
- `docs/acceptance-criteria.md`에서 대상 `# T-n 인수 조건`의 해당 규칙 블록을 읽는다 —
특히 `## 이유`에 1단계에서 메모해 둔 기존 검증 순서가 있으면 그대로 따른다.
- 실패하는 테스트 코드 자체를 읽어 무엇을 assert하는지 정확히 파악한다.

## 2. 실패 원인과 수정 지점 파악

- 테스트가 호출하는 API를 따라 관련 서비스/컨트롤러 메서드를 찾는다. 소스 루트와 계층 구조는`CLAUDE.md`의 아키텍처 설명을 먼저 확인한다.
- `CLAUDE.md`에 아직 정리되지 않은 중복이어도, 같은 검증/변환 로직이 여러 메서드에 중복돼 있을
수 있다는 전제로 실패하는 테스트가 다루는 필드/정책을 검색해 다른 등장 위치가 있는지 확인한다.
- 기존 검증이 어떤 순서로 실행되는지 확인한다(예: "값이 있는지" 먼저 → "있다면 모양이 맞는지"
그다음). 새 검증을 끼워 넣을 위치를 그 순서 안에서 정한다 — 순서를 바꾸지 않는다.

## 3. 최소 변경 설계

- 실패하는 테스트를 통과시키는 데 필요한 변경만 한다. 테스트가 요구하지 않는 리팩터링, 중복 제거, 추상화 도입을 함께 하지 않는다 — 이 저장소는 의도적으로 레거시 스타일(중복 허용, 긴 메서드)을유지한다.
- 2단계에서 찾은 중복 지점이 여러 곳이면, 테스트가 요구하는 경로뿐 아니라 같은 정책을 담고 있는
다른 경로도 함께 고친다 — 한쪽만 고치면 그 티켓의 요구사항이 나머지 경로에서 여전히 깨진 채로
남는다.
- 에러 처리는 이 프로젝트에 이미 있는 관례(예외 타입, 메시지 형식, 컨트롤러가 상태 코드로
변환하는 방식)를 그대로 따른다. 새 방식을 만들지 않는다.

## 4. 코드 수정

- `src/main/java` 안에서만 변경한다. 테스트 코드(`src/test/java`)나 `docs/*.md`는 이 단계에서
건드리지 않는다 — 인수 조건이 바뀔 일이 생기면 조용히 고치지 않고 사용자에게 알린다.

## 5. 완료 기준

방금 고친 테스트 클래스를 다시 실행해(명령은 0단계와 같다, `docs/plan.md`의 "특정 테스트
클래스만 실행"), 대상 테스트가 전부 통과하고 관련된 기존 테스트가 회귀 없이 통과하면 완료다.

- 결과를 못 읽으면 완료로 치지 않고 멈춘다(`docs/principles.md` "확인이 안 되면 통과가 아니다").
- 실패하던 메서드가 전부 통과해야 완료다. 여전히 실패하면 원인을 다시 짚는다 — assert를
약화시켜 통과시키지 않는다.
- 이번에 건드린 코드와 같은 클래스/같은 API를 다루는 다른 기존 테스트 파일이 있으면 함께 실행해,
이번 변경이 그 테스트를 깨뜨리지 않았어야 완료다 (전체 스위트 재실행은 4단계 몫이므로 여기서는
관련된 파일만 돈다).
- 위 두 조건(대상 테스트 통과, 관련 기존 테스트 회귀 없음)이 모두 갖춰져야 완료이며, 완료되면
`.claude/gate/gate` 디렉터리를 만들고(`mkdir -p .claude/gate`) `.claude/gate/armed` 파일을
만든다(`touch`). 이 지점부터는 테스트가 통과 상태를 유지해야 하므로 Stop 훅이 매 턴 끝마다
전체 스위트로 다시 확인하도록 무장한다.

## 6. 마무리 보고

- 어떤 티켓/요구사항을 다뤘는지, 어떤 파일의 어느 메서드를 고쳤는지, 중복 지점을 몇 곳 함께
고쳤는지, 대상 테스트가 이제 통과하는지 요약한다.
- 코드를 읽다가 `acceptance-criteria.md`에 없는 규칙(예: 침묵하던 정책)을 만났다면, 이 자리에서
판단해 고치지 않는다 — 사용자에게 알리고 `docs/tickets.md`에 남길지 확인한다(형식은
`docs/plan.md`의 "새 티켓 남기기" 참고, 4단계 원칙이지만 구현 중 흔히 마주치므로 미리 적용한다).
- 전체 테스트 재실행과 커밋은 4단계(판정)의 몫이라는 것을 안내하고 멈춘다.
