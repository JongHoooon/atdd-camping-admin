# 인수 조건 작성

`docs/plan.md`의 1단계("인수 조건")를 처리한다. 이 스킬은 **1단계까지만** 담당한다.
인수 테스트 작성(2단계)이나 구현(3단계)에는 관여하지 않는다 — 코드나 테스트 파일을 건드리지 않는다.

이 스킬을 시작하기 전에 `docs/principles.md`와 `docs/plan.md`를 아직 읽지 않았다면 먼저 읽는다.

## 사용 예시

```
/acceptance-criteria T-4
```

동작 흐름: `docs/tickets.md`의 `T-4` 항목을 읽고, 요구사항이 하나로 명확하면 추가 질문 없이진행한다. 서버를 직접 실행해 호출해 실측하고, 그중 일부 경로에서만 검증이 빠져 있는 버그를 확인했다면 그 결과를 `docs/acceptance-criteria.md`에 `# T-4 인수 조건` 블록으로 남긴다.

## 0. 입력 확인

인자로 티켓 ID(`T-n`)를 받는다.

- 인자가 없으면 `docs/tickets.md`를 읽어 아직 `docs/acceptance-criteria.md`에 `# T-n 인수 조건`
블록이 없는 티켓 목록을 보여주고, 어떤 티켓을 다룰지 AskUserQuestion으로 묻는다.
- **"이 티켓에서 다룰 요구사항 설명"이 인자로 주어지지 않았다면, 스스로 명확한지 애매한지
판단해서 넘어가지 않는다 — 예외 없이 매번** `docs/tickets.md`에서 해당 티켓 본문을 그대로
보여주고, 이번에 다룰 요구사항이 무엇인지 AskUserQuestion으로 사용자에게 확인한다. 티켓
본문이 요구사항 문장처럼 짧고 단순해 보여도(예: 고객센터 신고 한 줄) 자체 판단으로 요구사항을
확정하지 않는다 — 신고 문구는 증상일 뿐 요구사항(정책의 정확한 경계)이 아닐 수 있다.
- 인자로 요구사항 설명이 이미 주어졌으면 그것을 범위로 삼되, 티켓 본문과 어긋나거나 범위가
애매하면 마찬가지로 AskUserQuestion으로 확인한다.
- 이 확인 질문 없이 2단계(컨텍스트 로드)로 넘어가지 않는다.

## 1. 컨텍스트 로드

다음을 읽는다:

- `docs/principles.md`, `docs/plan.md`
- `docs/acceptance-criteria.md`, `docs/tickets.md`

`docs/acceptance-criteria.md`에서 가장 마지막 `# T-n 인수 조건` 블록과 `docs/tickets.md`에서
가장 큰 `T-n` 번호를 확인해, 새 티켓을 만들어야 할 때 다음 번호를 알아 둔다.

## 2. 코드에서 현재 동작 파악

- 티켓이 언급한 기능과 관련된 코드를 찾는다. 
- 관련 검증이 어떤 순서로 실행되는지(무엇을 먼저 체크하는지) 메모해 둔다 — 3단계(구현)에서
이 순서를 지켜야 하므로, 여기서 파악한 것을 `이유`에 남긴다.

## 3. 실제 서버 기동

- `docs/plan.md`의 "이 저장소의 실행 방법"을 따라 서버를 띄운다.
- 가벼운 엔드포인트를 폴링하거나 로그를 확인해 기동이 끝났음을 확인한 뒤에만 다음 단계로 넘어간다.

## 4. 경계 예시 설계 및 실측 — 응답을 지어내지 않는다

이번 단계의 핵심 원칙(`docs/principles.md` "실측에 근거한 판정"): **코드를 읽고 응답을 추정해서
쓰지 않는다. 모든 예시는 실제로 `curl`을 호출해 받은 응답을 그대로 옮긴다.**

규칙 하나당 블록 하나로 묶는다: 규칙 한 줄, 그 규칙이 필요한 이유, 공통 `Given` 하나, 그 아래
여러 개의 `When → Then` 쌍. `Given`이 없으면 예시로 치지 않는다 — 나중에 시드 데이터가 바뀌었을
때 이 예시가 왜 그 응답을 받았는지 알 수 없게 된다.

요구사항마다 최소 아래 경계를 설계해 실측한다:

1. 허용되는 경계값 (예: "30일 이내"라면 정확히 30일째)
2. 그 경계를 첫 번째로 벗어나는 값 (31일째)

각 실측 결과를 분류한다:

| 라벨 | 의미 |
| --- | --- |
| `버그` | 요구사항과 다르게 동작한다 — `Then` 줄에 실제 응답과 기대 응답을 함께 적는다(`(버그) <실제> → 기대 <기대>`) |
| `정상` | 이미 요구사항대로 동작한다 |
| `정상, 회귀 방지` | 이미 정상이지만 이번에 처음 인수 조건으로 명시 — 앞으로 안 깨지게 고정 |
| `참고용` | 관련은 있으나 이 요구사항의 정식 조건은 아님 — 별도 티켓 후보 (6단계 참고) |

실측하다가 판단이 필요한 지점을 만나면 같은 블록에 `질문` 줄로 남긴다 — 형식은 5단계 템플릿을
따른다.


## 5. `docs/acceptance-criteria.md`에 작성

파일 끝에 아래 형식을 그대로 이어 붙인다. 신규 티켓이면 `# T-n 인수 조건` 헤더와 티켓의
신고/요청 문구를 한 줄로 인용한 뒤 바로 규칙 블록을 이어 붙인다. 기존 티켓에 규칙을 추가하는
것이면 그 티켓의 마지막 규칙 블록 뒤, 다음 `---` 앞자리에 새 블록을 끼워 넣는다.

~~~markdown
# T-n 인수 조건

<티켓의 신고/요청 문구를 한 줄로 인용>

```
규칙   <규칙 한 줄 서술 — 트리거 조건과 적용 범위(예: 어느 API 경로에 적용되는지)를 포함한다>
이유   <왜 이 규칙이 필요한지. 관련 코드 file:line을 인용해도 된다>

Given  <사전 상태 — 기준일, 쓰인 시드 데이터, 기존 상태 등>
When   <실제로 호출한 요청>                    Then  <실측한 응답 코드/메시지> (<라벨>)
When   <경계를 벗어난 요청>                    Then  (버그) <실측한 실제 응답> → 기대 <기대 응답>

질문   <이 규칙을 실측하다 만난, 판단이 필요한 지점 — 없으면 이 줄과 다음 줄은 생략>
       → <무엇이 애매한지, 왜 이 티켓 범위 밖인지. T-<n>로 분리, 이 티켓에서는 판단하지 않는다.>
```

```
규칙   <같은 티켓 안의 다음 규칙>
이유   ...

Given  ...
When   ...                                  Then  ...
```

---
~~~

한 블록 안에 `When → Then` 쌍을 실측한 개수만큼 나열한다. `질문`은 그 규칙을 실측하며 판단이
필요한 지점을 만났을 때만 붙이고, 없으면 생략한다. 한 티켓에 규칙이 여러 개면 규칙마다 별도
블록(triple backtick 하나)으로 나누고 빈 줄로 구분한다 — `docs/acceptance-criteria.md`에 이미
쌓인 이전 티켓 블록이 있으면 그 구조를 그대로 따르고, 이 파일이 아직 비어 있다면(첫 티켓) 위
형식 그대로 시작한다.

## 6. 판단이 필요한 지점 처리

- **이 티켓 범위 안에서** 결정해야 하는데 요구사항이 애매하면, 그 자리에서 AskUserQuestion으로
묻는다 (`docs/plan.md` 1단계 AI 지시 — "판단이 필요한 부분은 질문한다").
- **이 티켓 범위 밖**에서 발견됐거나 요구사항 자체가 침묵하는 정책(예: 유일성 제약처럼 누구도
정한 적 없는 규칙)은 스스로 판단하지 않는다. 해당 규칙 블록에 `질문` 줄로 남기고(5단계 형식),
`docs/tickets.md`에도 새 티켓으로 남긴다. `docs/tickets.md`에 이미 있는 항목과 같은 형식으로
남긴다:

```markdown
T-<n> <제목>

내용: T-<원본 티켓> 작업 중 확인. <발견 경위와 관련 코드 file:line 인용>
<무엇이 애매한지>는 요구사항이 침묵하므로 이 티켓에서는 판단하지 않는다.

---
```

- 4단계에서 `참고용`으로 분류한 예시가 있고 아직 정식 조건으로 다뤄진 적 없다면, 그 자체를
후속 티켓으로 남길지 검토한다.

## 7. 마무리 전 확인 — "넘어가기 전에" 확인

`docs/plan.md` 1단계의 "넘어가기 전에" 조건: **예시가 직접 호출해 받은 응답인지 확인한다.**

- `docs/acceptance-criteria.md`에 적은 모든 "실측 응답"이 이번 세션에서 실제로 curl한 결과인지
다시 확인한다. 재사용하거나 추정한 값이 하나라도 있으면 다시 호출해 바꾼다. 하나라도 확인이
안 되면 다음 단계로 넘어가지 않는다.
- `docs/tickets.md`에 새 티켓을 추가했다면 번호가 겹치지 않는지, `---`로 다른 항목과 구분됐는지
확인한다.
- 코드나 테스트 파일은 건드리지 않았는지 확인한다 — 이 스킬은 2단계(인수 테스트) 이전에서 멈춘다.
- 작업 요약을 짧게 보고한다: 어떤 요구사항을 몇 개의 예시로 실측했는지, 새로 생긴 티켓이 있는지,
아직 열려 있는 질문이 있는지.
