# 인수 조건 작성

`docs/plan.md`의 1단계("인수 조건")를 처리한다. 이 스킬은 **1단계까지만** 담당하며,
코드나 테스트 파일을 건드리지 않는다.

## 멈추는 조건

이 스킬이 완료 기준에 도달하지 못한 채 멈추려 하면, 왜 멈추는지 아래 3가지 중 하나로 스스로
판단해 `docs/rotations.md`에 한 줄 남긴다(질문을 던지고 답을 받아 같은 실행 안에서 계속
이어간다면 남기지 않는다):

- **회색지대**: 판단이 필요한 지점이라 AskUserQuestion으로 묻고 멈춘다.
- **맴돌다 끊김**: 같은 원인으로 제자리걸음이라고 스스로 판단되면 멈추고 사람을 부른다 —
  테스트가 실패했다는 사실 자체는 이유가 아니다(TDD 특성상 정상적인 실패일 수 있다).
- **예산 소진**: 컨텍스트/턴 예산이 바닥나 완료 기준에 도달하지 못하고 멈춘다.

## 사용 예시

```
/acceptance-criteria T-4
```

동작 흐름: `docs/tickets.md`의 `T-4` 항목을 읽고, 요구사항이 하나로 명확하면 추가 질문 없이진행한다. 서버를 직접 실행해 호출해 실측하고, 그중 일부 경로에서만 검증이 빠져 있는 버그를 확인했다면 그 결과를 `docs/acceptance-criteria.md`에 `# T-4 인수 조건` 블록으로 남긴다.

## 0. 입력 확인

아래 명령으로 `.claude/gate/state.json`에 이 스킬이 시작됐음을 기록한다 — Stop 훅이 이 스킬이
완료 기준에 못 미친 채 멈출 때 `docs/rotations.md`에 기록을 남겼는지 확인하는 데 쓴다:

```bash
mkdir -p .claude/gate && jq -n --arg s "acceptance-criteria" --argjson rb "$(wc -l < docs/rotations.md | tr -d ' ')" '{current_skill:$s, completed:false, rotations_baseline:$rb}' > .claude/gate/state.json
```

인자로 티켓 ID(`T-n`)를 받는다.

- 인자가 없으면 `docs/tickets.md`를 읽어 아직 `docs/acceptance-criteria.md`에 `# T-n 인수 조건`
블록이 없는 티켓 목록을 보여주고, 어떤 티켓을 다룰지 AskUserQuestion으로 묻는다.
- **"이 티켓에서 다룰 요구사항 설명"이 인자로 주어졌으면 그것을 범위로 삼아 바로 다음 단계로
넘어간다.** 인자로 주어지지 않았다면 `docs/tickets.md`에서 해당 티켓 본문을 그대로 이번에 다룰
요구사항으로 삼는다. 티켓 본문이 요구사항 문장처럼 짧고 단순해 보여도(예: 고객센터 신고 한 줄)
그 문구를 그대로 요구사항으로 채택한다 — 신고 문구가 증상일 뿐 요구사항(정책의 정확한 경계)이
아닐 수 있다는 것은 여기서 멈춰 확인하지 않고, 이후 단계(4단계 경계 실측, 6단계 판단이 필요한
지점 처리)에서 코드와 실측으로 확인해 규칙으로 적는다.
- 이 단계는 사람의 확인을 기다리지 않는다. 범위가 정말 애매해 이 티켓 안에서 결정해야 하는
지점은 6단계("판단이 필요한 지점 처리")의 절차를 그대로 따른다 — 그 자리에서 AskUserQuestion으로
묻거나 `tickets.md`에 남긴다.

## 2. 코드에서 현재 동작 파악

- 관련 검증이 어떤 순서로 실행되는지(무엇을 먼저 체크하는지) 메모해 둔다 — 3단계(구현)에서
이 순서를 지켜야 한다.

## 3. 실제 서버 기동

- `docs/plan.md`의 "이 저장소의 실행 방법"을 따라 서버를 띄운다.
- 가벼운 엔드포인트를 폴링하거나 로그를 확인해 기동이 끝났음을 확인한 뒤에만 다음 단계로 넘어간다.

## 4. 경계 예시 설계 및 실측 — 응답을 지어내지 않는다

이번 단계의 핵심 원칙(`docs/principles.md` "실측에 근거한 판정"): **코드를 읽고 응답을 추정해서
쓰지 않는다. 모든 예시는 실제로 `curl`을 호출해 받은 응답을 그대로 옮긴다.**

규칙 하나당 블록 하나로 묶는다: 규칙 한 줄, 그 규칙이 필요한 이유, 공통 `Given` 하나, 그 아래
여러 개의 `When → Then` 쌍. `Given`이 없으면 예시로 치지 않는다 — 나중에 시드 데이터가 바뀌었을
때 이 예시가 왜 그 응답을 받았는지 알 수 없게 된다.

**`Given`은 `data.sql` 시드 row를 그대로 재사용하지 않는다.** 검증에 필요한 데이터는 실제 생성
엔드포인트를 호출해 직접 만들고, 그 응답에서 나온 값을 `Given`으로 삼는다. 시드 row를 그대로
쓰면 (1) `data.sql`이 나중에 바뀌었을 때 예시가 조용히 깨지고, (2) 인수 테스트 단계에서 여러
테스트가 같은 row를 놓고 경합하게 된다. 시드 데이터 자체의 결함(예: 시드 무결성 버그)을 다루는
티켓처럼 시드 row 자체가 검증 대상일 때만 예외로 삼고, 왜 예외인지 `이유`에 남긴다.

**생성 엔드포인트가 없거나(예: 이 저장소는 예약(Reservation)·고객(Customer)을 만드는 API가
없다), 있어도 필요한 조건을 만들 수 없으면(예: 대여·판매 생성 API는 날짜를 파라미터로 받지
않고 항상 서버의 "지금"으로 고정돼, 과거 날짜 데이터를 API로는 만들 수 없다) — 시드에 기대는
대신 그 규칙 전용으로 필요한 값만 SQL을 직접 실행해 넣는다.** H2는 인메모리라 서버를 껐다 켜면
사라지므로, 이 방식으로 넣은 데이터도 이번 실측에서 직접 실행해 확인한 것이어야 한다(추정 금지
원칙은 동일). 시드를 그대로 재사용하는 것보다는 필요한 값만 SQL로 직접 넣는 쪽을 우선한다 —
시드는 프로젝트 전역이 공유하는 자원이라 나중에 바뀌거나 다른 티켓과 충돌할 수 있지만, 직접
넣은 SQL 데이터는 이 규칙이 무엇을 필요로 했는지 `Given`에 그대로 드러난다. 다만 규칙 3처럼
"기간에 걸쳐 여러 날짜에 흩어진 데이터의 합계가 일치하는지" 검증하는 경우처럼 시드가 이미 그
조건(여러 날짜에 걸친 데이터)을 갖추고 있고 새로 넣은 SQL 데이터와 시드를 구분할 수 없어 순수
SQL만으로는 검증이 어려운 경우는 예외로 시드를 함께 쓸 수 있다. `Given`엔 어떤 부분이 시드고
어떤 부분을 직접 넣었는지 구분해 남기지 않는다 — 그런 출처 구분은 개발 관점의 정보라 업무
용어로 쓰는 `Given`엔 맞지 않는다.

요구사항마다 최소 아래 경계를 설계해 실측한다:

1. 허용되는 경계값 (예: "30일 이내"라면 정확히 30일째)
2. 그 경계를 첫 번째로 벗어나는 값 (31일째)

각 실측 결과를 분류한다:

| 라벨 | 의미 |
| --- | --- |
| `버그` | 요구사항과 다르게 동작한다 — `Then` 줄에 실제 응답과 기대 응답을 함께 적는다(`(버그) <실제> → 기대 <기대>`) |
| `정상` | 이미 요구사항대로 동작한다 |
| `정상, 회귀 방지` | 이미 정상이지만 이번에 처음 인수 조건으로 명시 — 앞으로 안 깨지게 고정 |
| `참고용` | 관련은 있으나 이 요구사항의 정식 조건은 아님 — 별도 티켓 후보 (6단계 참고) |

실측하다가 판단이 필요한 지점을 만나면 같은 블록에 `질문` 줄로 남긴다 — 형식은 5단계 템플릿을
따른다.

`When`/`Then` 줄에는 실제로 호출/응답받은 요청·응답 JSON 전문을 그대로 옮기지 않는다. 무엇을
바꿨는지와 그 결과가 무엇인지를 간결한 자연어로 요약한다 — 예:

```
Given  시드가 쓰지 않는 사이트
When   시작일이 오늘 + 29일    Then  201 Created, 확인 코드 발급
When   시작일이 오늘 + 31일    Then  409 "예약 시작일은 오늘로부터 30일 이내여야 합니다."
```

값 자체가 쟁점(기대값과 실제값 비교, 특히 `버그` 라벨)일 때만 그 필드 값을 구체적으로 적는다.
JSON 요청 바디나 전체 응답 바디를 옮기는 대신 "재고를 99로 수정" 같은 서술로 무엇을 호출했는지
표현하고, 실측은 여전히 3단계에서 직접 호출해 확인한 결과여야 한다 — 표현만 간결해질 뿐, 응답을
추정해서 쓰지 않는다는 원칙은 그대로 적용된다.


## 5. `docs/acceptance-criteria.md`에 작성

파일 끝에 아래 형식을 그대로 이어 붙인다. 신규 티켓이면 `# T-n 인수 조건` 헤더와 티켓의
신고/요청 문구를 한 줄로 인용한다. 0단계에서 확인한 "이 티켓에서 다룰 요구사항"이 티켓 본문을
그대로 옮긴 것이 아니라 별도 문장(인자로 받았거나 AskUserQuestion으로 확정한 것)이면, 그 문장도
`요구사항:` 줄로 바로 아래에 이어 적는다 — 티켓 문구는 증상이고 요구사항은 확정된 범위이므로
둘 다 남겨야 나중에 왜 이 범위로 정했는지 추적할 수 있다. 그런 다음 규칙 블록을 이어 붙인다.
기존 티켓에 규칙을 추가하는 것이면 그 티켓의 마지막 규칙 블록 뒤, 다음 `---` 앞자리에 새 블록을
끼워 넣는다.

~~~markdown
# T-n 인수 조건

<티켓의 신고/요청 문구를 한 줄로 인용>

요구사항: <이 티켓에서 다룰 요구사항 문장 — 티켓 문구와 동일하면 이 줄은 생략>

```
규칙   <규칙 한 줄 서술 — HTTP 메서드/경로 대신 업무 용어로 트리거 조건과 적용 범위를 쓴다
       (예: "PUT /admin/products/{id} 요청으로" 대신 "상품 정보를 수정하면")>
이유   <왜 이 규칙이 필요한지. 1~2줄로 간결하게 — 관련 코드 file:line은 인용해도 되지만
       구현 세부사항을 길게 설명하지 않는다>

Given  <사전 상태 — 무엇이 있는지를 업무 용어로만, 부연 설명 없이 간결하게>
When   <무엇을 바꿨는지 자연어로 간결히>     Then  <실측한 결과 요약> (<라벨>)
When   <경계를 벗어나게 바꾼 경우>          Then  (버그) <실측한 실제 결과> → 기대 <기대 결과>

질문   <이 규칙을 실측하다 만난, 판단이 필요한 지점 — 없으면 이 줄과 다음 줄은 생략>
       → <무엇이 애매한지, 왜 이 티켓 범위 밖인지. T-<n>로 분리, 이 티켓에서는 판단하지 않는다.>
```

`규칙`/`이유` 모두 API 경로·컨트롤러 메서드명 같은 구현 세부사항을 노출하지 않는다
(`docs/test-guide.md`의 테스트 네이밍 원칙과 같은 이유 — 업무 정책을 드러내야 나중에
구현이 바뀌어도 조건 자체는 그대로 남는다). 그런 세부사항이 왜 이 규칙이 필요한지 설명하는 데
꼭 필요하면 `이유`에 `file:line`만 짧게 인용하고, 코드 동작을 문장으로 풀어 쓰지 않는다.

**`Given`/`When`/`Then`도 개발 용어를 걷어내고 일반적인 문장으로 간결하게 쓴다.** 상품 ID,
API 경로, DB 테이블·컬럼명, 응답 필드명(occurredAt, grandTotalRevenue 등), 타임스탬프,
재시도·PK 충돌 같은 구현 경위는 적지 않는다 — 비개발자가 읽어도 "무엇이 주어졌고 무엇을
했더니 무엇이 나왔는지"만으로 이해할 수 있어야 한다. 왜 이 데이터를 이렇게 만들었는지
같은 부연 설명도 넣지 않는다 — `Given`은 결과 상태만 짧게 적는다(예: "랜턴 상품(id=1)으로
워크인 대여 생성 API 호출(T-9 PK 충돌 재시도로 2건 저장됨)" 대신 "오늘 랜턴 대여 2건").
실측 자체는 여전히 정확해야 하므로, 값 자체가 쟁점인 경우(특히 `버그` 라벨)의 구체적인
수치·이름은 그대로 남긴다.

```
규칙   <같은 티켓 안의 다음 규칙>
이유   ...

Given  ...
When   ...                                  Then  ...
```

---
~~~

한 블록 안에 `When → Then` 쌍을 실측한 개수만큼 나열한다. `질문`은 그 규칙을 실측하며 판단이
필요한 지점을 만났을 때만 붙이고, 없으면 생략한다. 한 티켓에 규칙이 여러 개면 규칙마다 별도
블록(triple backtick 하나)으로 나누고 빈 줄로 구분한다 — `docs/acceptance-criteria.md`에 이미
쌓인 이전 티켓 블록이 있으면 그 구조를 그대로 따르고, 이 파일이 아직 비어 있다면(첫 티켓) 위
형식 그대로 시작한다.

## 6. 판단이 필요한 지점 처리

- **이 티켓 범위 안에서** 결정해야 하는데 요구사항이 애매하면, 그 자리에서 AskUserQuestion으로
묻는다 (`docs/plan.md` 1단계 AI 지시 — "판단이 필요한 부분은 질문한다").
- **이 티켓 범위 밖**에서 발견됐거나 요구사항 자체가 침묵하는 정책(예: 유일성 제약처럼 누구도
정한 적 없는 규칙)은 스스로 판단하지 않는다. 해당 규칙 블록에 `질문` 줄로 남기고(5단계 형식),
`docs/tickets.md`에도 새 티켓으로 남긴다 — 형식(제목/내용/`필요:`/번호 매기기)은
`docs/plan.md`의 "새 티켓 남기기"를 그대로 따른다.
- 4단계에서 `참고용`으로 분류한 예시가 있고 아직 정식 조건으로 다뤄진 적 없다면, 그 자체를
후속 티켓으로 남길지 검토한다.

## 7. 완료 기준

모든 실측 응답이 직접 호출해 받은 것이고, 회색지대 점검을 서브에이전트가 마쳤고, 코드나
테스트 파일을 건드리지 않았으면 완료다.

- `docs/acceptance-criteria.md`에 적은 모든 "실측 응답"이 이번 세션에서 실제로 curl한 결과여야
완료다. 재사용하거나 추정한 값이 하나라도 있으면 다시 호출해 바꾼다. 하나라도 확인이
안 되면 완료가 아니다 — 다음 단계로 넘어가지 않는다.
- **회색 지대가 없어야 완료다 — 이 확인은 이 세션이 직접 하지 않고 새 — 이 확인은 이 세션이 직접 하지 않고 새
서브에이전트에게 맡긴다.** 방금 쓴 규칙을 쓴 세션 스스로는 작성 당시엔 자연스러워 보였던
확대·축소 해석을 잘 못 잡는다(`docs/principles.md` "만드는 쪽과 판정하는 쪽의 분리"와 같은
이유). Agent 도구로 서브에이전트를 띄우고, 이번에 다룬 티켓 번호, 요구사항 문장, 방금
`docs/acceptance-criteria.md`에 새로 추가한 블록 전문(규칙/이유/Given/When/Then/질문)을
그대로 넘긴 뒤 아래를 점검해 보고하게 한다 — 서브에이전트는 이 세션의 조사 과정을 모르므로
처음부터 코드를 다시 조사시키지 말고 넘겨준 블록과 필요하면 관련 코드 파일만 읽게 한다:
  - `규칙`이 요구사항 문구를 문자 그대로 넘어서 확대·축소 해석한 곳이 있는가(예: "어느
    리포트에서 보든"처럼 특정 시점 비교로 읽히는 문구를, 시점과 무관한 데이터 무결성 요구로
    넓혀 해석하는 식).
  - `Given`이 `data.sql` 시드 row를 재사용한 곳이 있는가 — 검증 대상 레코드 자체는 아니더라도
    합계·집계처럼 구조상 시드를 배제할 수 없는 경우가 있다. 생성 엔드포인트가 없거나 필요한
    조건(과거 날짜 등)을 API로 만들 수 없는 경우 시드 대신 SQL을 직접 실행해 데이터를
    넣었어야 하는데 시드를 그대로 재사용한 곳은 없는가(코드·data.sql을 직접 확인해 판단한다 —
    `Given`에 시드 여부가 표시돼 있길 기대하지 않는다).
  - SQL로 직접 넣은 데이터가 있다면, 다른 시드 row(특히 같은 상품·같은 날짜로 잡히는 row)와
    겹쳐 `Then`에 적은 개수·합계가 실제와 달라지는 곳은 없는가.
  - `Given`에 적은 개수·조건이 실제로 호출한 횟수·상태와 정확히 일치하는가(재시도나 부수
    효과로 의도보다 더 많이/다르게 생성된 데이터가 있는데 문서엔 반영 안 된 경우).

  서브에이전트가 지적한 항목은 그 자리에서 조용히 고치지 말고, 이 티켓 범위 안에서 판단할
  수 있는 것은 AskUserQuestion으로 확인하고 범위 밖이거나 요구사항이 침묵하는 것은 `질문`
  줄과 `tickets.md` 새 티켓으로 남긴다(6단계와 동일한 절차).
- `docs/tickets.md`에 새 티켓을 추가했다면 `docs/plan.md`의 "새 티켓 남기기" 형식을 지켰어야
완료다.
- 코드나 테스트 파일은 건드리지 않았어야 완료다 — 이 스킬은 2단계(인수 테스트) 이전에서 멈춘다.
- 위 조건을 모두 갖춰 진짜로 완료됐으면 아래 명령으로 `.claude/gate/state.json`에 `completed`를
표시한다:
  ```bash
  jq '.completed=true' .claude/gate/state.json > .claude/gate/state.json.tmp && mv .claude/gate/state.json.tmp .claude/gate/state.json
  ```
- 작업 요약을 짧게 보고한다: 어떤 요구사항을 몇 개의 예시로 실측했는지, 새로 생긴 티켓이 있는지,
아직 열려 있는 질문이 있는지.
