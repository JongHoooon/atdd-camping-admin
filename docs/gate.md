# 테스트 게이트 (Stop 훅)

`docs/plan.md`의 각 단계("넘어가기 전에: ~통과하는지 확인한다")를 AI 진술이 아니라 도구 실행으로
강제하기 위한 장치다. 턴이 끝나려는 시점(Stop)마다 전체 테스트를 실제로 돌려, 실패하면 턴을
막는다.

## 구성 요소

- `.claude/settings.json`의 `Stop` 훅 — 턴 종료 시점마다 아래 명령을 실행한다:
  ```
  if [ ! -f .claude/gate/armed ]; then exit 0; fi
  .claude/gate/gate-check.sh
  ```
- `.claude/gate/armed` — 무장 마커. 없으면 훅이 즉시 통과시킨다(휘발성, `.gitignore`).
  - `.claude/skills/acceptance-test/SKILL.md` 0단계에서 **지운다**(무장 해제) — 지금부터
    실패하는 인수 테스트를 새로 쓰는 구간이라, 정상적으로 빨간불인 상태를 훅이 막지 않게 한다.
  - `.claude/skills/implementation/SKILL.md` 5단계에서 **만든다**(무장) — 대상 테스트가
    통과하고 회귀가 없음을 스스로 확인한 뒤. 이제부터는 통과 상태를 지켜야 한다는 신호다.
- `.claude/gate/gate-check.sh` — 실제 판정 스크립트(커밋 대상, 실행 권한 있음). 테스트를 돌려
  성공하면 통과시키고, 실패하면 실패한 테스트 이름(`classname#name`)별로 `.claude/gate/state.json`
  에 횟수를 세어 한계 도달 여부를 판정한다.
- `.claude/gate/state.json` — 지금 사이클의 이름별/전체 카운터(휘발성, `.gitignore`). 통과하거나
  한계에 도달해 사람에게 넘길 때 삭제된다.
- `.claude/gate/record.log` — 막힌 줄(`BLOCK`)/넘긴 줄(`HANDOFF`)/통과한 줄(`PASS`)의 감사
  기록(커밋 대상). 카운터는 사이클마다 리셋돼도 "언제 무슨 일이 있었는지"는 여기 남는다.

## 정상 동작 흐름 (설계 의도)

`BLOCK`이 뜨면(테스트 실패) AI는 그 실패를 보고 실제로 원인을 찾아 코드나 테스트를 고친 뒤
다시 턴을 끝내려 시도해야 한다. 즉:

1. 턴 종료 시도 → 테스트 실패 → `BLOCK`(1번째) → 실패 원인을 분석해 고침
2. 다시 턴 종료 시도 → (고친 게 맞으면) 통과 → `PASS`로 끝남
   - (고친 게 틀렸거나 다른 게 깨지면) → `BLOCK`(2번째) → 다시 고침
3. 보통은 한계에 닿기 전에 고쳐서 끝난다.

한계는 "같은 이유로 계속 실패해 AI 혼자 못 고치고 있다"는 신호가 나왔을 때 사람에게 넘기기
위한 안전장치다 — AI가 계속 같은 자리를 돌며 시간과 비용을 태우는 것을 막는다.

- **이름별 한계: 3** — 같은 테스트가 같은 이유로 3번 막히면 그 시도 방식 자체가 틀렸을
  가능성이 높다. 더 도는 것보다 사람이 보는 게 낫다.
- **통째 한계: 5** — 서로 다른 테스트를 번갈아 오가며 막힐 수 있어 이름별 한계만으로는 못
  잡는 경우를 대비한다. 이름별 한계보다 넉넉히 잡아 서로 다른 원인 한두 개는 스스로 풀 여유를
  준다.

## 종료 코드별 실제 동작 (실측 확인, 2026-08-25)

의도적으로 테스트를 깨고 실제 Stop 훅을 여러 차례 발동시켜 직접 확인했다:

| 종료 코드 | 상황 | 실제로 보이는 곳 |
|---|---|---|
| `0` (PASS) | 테스트 통과 | 아무에게도 안 보임 — 조용히 턴이 끝남 |
| `2` (BLOCK) | 실패, 한계 미도달 | AI에게 `Stop hook feedback`으로 전달됨 — 턴이 안 끝나고 AI가 그 내용을 보고 계속함 |
| `1` (HANDOFF) | 실패, 한계 도달 | **사람에게** `Stop hook error: Failed with non-blocking status code: ...` 배너로 직접, 즉시 노출됨 — 턴은 그대로 끝남(차단 아님) |

애초 스크립트는 `HANDOFF`도 `exit 0`을 썼는데, 이 경우 `PASS`와 똑같이 조용히 지나가 사람이
한계 도달을 알아챌 능동적인 방법이 전혀 없었다(사후에 `record.log`를 열어봐야만 구분 가능).
`exit 1` + stderr 메시지로 바꾼 뒤 실제 턴 종료로 재현해, 사람에게 배너가 즉시 뜨는 것을
확인했다. 이후 `.claude/gate/gate-check.sh`는 `HANDOFF` 시 `exit 1`을 쓴다.

넘어온 뒤에도 게이트는 다시 선다 — `HANDOFF`는 `state.json`만 지울 뿐 무장(`armed`) 자체를
풀지 않으므로, 같은 원인으로 다음 실패가 나면 카운터가 1부터 다시 쌓이며 정상적으로 막는다
(실측 확인: `HANDOFF` 직후 같은 테스트가 여전히 깨진 채 다음 시도 → `BLOCK`(count=1)).

## 한계 — 무엇을 강제하고 무엇을 강제하지 않는가

이 게이트가 실제로 강제하는 건 딱 하나다: **턴이 끝나는 시점에 전체 테스트 스위트가 실제로
녹색이어야 한다**는 것. `./gradlew test --rerun-tasks`를 직접 돌려 종료 코드를 보므로,
"통과했다"는 AI의 말만으로는 턴을 끝낼 수 없다.

**그 초록불이 어떻게 만들어졌는지는 전혀 보지 않는다.** `gate-check.sh`는 JUnit XML에서
"실패한 테스트가 있는가"만 볼 뿐, `git diff` 내용을 판단하지 않는다. 그래서 아래 셋을
구분하지 못한다:

- 프로덕션 코드의 원인을 실제로 고친 경우
- 테스트의 assert를 실제 관찰값에 맞춰 바꿔치기한 경우(예: `isEqualTo(0f)`를
  `isEqualTo(999f)`로 — 요구사항이 아니라 지금 나오는 값에 맞춘 것)
- 실패하는 테스트를 지우거나 `@Disabled`를 붙인 경우

세 경우 모두 게이트는 똑같이 통과시킨다. 이건 의도적인 설계 공백이다 — 스크립트가 diff의
의미(이 assert 변경이 요구사항에 맞는 고침인지, 아니면 억지로 맞춘 것인지)까지 판단하기
시작하면 "스크립트가 판단하기 시작하면 선을 넘은 것"이라는 원칙을 어기게 된다.

대신 이 문제는 기계적 장치가 아니라 **쓰인 말(스킬 지시문)과 사람의 판단**에 맡겨져 있다:

- `implementation` 스킬 5단계 지시: "여전히 실패하면 원인을 다시 짚는다 — assert를
  약화시켜 통과시키지 않는다." — AI의 자기 규율에 기대는 문장이지 강제가 아니다.
- `verdict` 스킬 — 코드를 쓴 세션이 아닌 독립된 서브에이전트가 `git diff`를
  `acceptance-criteria.md`의 요구사항과 대조한다(`docs/principles.md` "만드는 쪽과
  판정하는 쪽의 분리"). assert가 요구사항과 다르게 바뀌었다면 이 대조에서 걸릴 가능성이
  있지만, 이것도 자동 검증이 아니라 그 서브에이전트가 실제로 꼼꼼히 봤을 때만 작동한다.

즉 이 게이트는 "테스트를 안 돌리고 통과를 주장하는 것"은 확실히 막지만, "테스트를 돌리되
그 테스트 자체를 조작해 억지로 통과시키는 것"은 막지 못한다.

## 참고

- 이 게이트는 `docs/*.md`를 전혀 읽지 않는다 — 순수하게 `.claude/gate/armed` 파일 존재 여부와
  테스트 실행 결과(XML)만 본다. 이 문서는 실행에 관여하지 않는, 사람이 참고할 설계 배경
  문서다.
- 원래 설계 결정 과정과 스크립트를 만들 때 시킨 지시문 전문은 `docs/enforcement.md`(작업
  완료 후 삭제 예정)에 있었다. 이 문서는 그중 앞으로도 유효한 내용만 옮겨 남긴 것이다.
