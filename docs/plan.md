# 작업 계획

티켓 하나를 처리하는 순서다. 지켜야 하는 것은 `principles.md`에 있다.

## 1. 인수 조건

- 입력: 티켓, 이 티켓에서 다룰 요구사항
- 하는 일: 코드에서 지금 동작을 파악하고, 요구사항과 어긋나는 자리를 판정한다
- 남기는 것: `acceptance-criteria.md`에 규칙과 예시와 이유. 못 정한 것은 질문으로, 남은 일은 `tickets.md`에
- 넘어가기 전에: 예시가 직접 호출해 받은 응답인지 확인한다
- AI에게 주는 지시: 
  - 경계는 직접 실제 서버를 띄워 호출해서 실측한다.
  - 예시는 given-when-then 구조로 작성한다.
  - `acceptance-criteria.md` 작성 중 판단이 필요한 부분은 질문한다.

## 2. 인수 테스트

- 입력: `acceptance-criteria.md`, `test-guide.md`
- 하는 일: 테스트 초안을 받아 규칙을 검증하는지 판정하고 실행한다
- 남기는 것: 테스트 코드. 초안에 준 제약은 `test-guide.md`에 규칙 한 줄로
- 넘어가기 전에: 인수 테스트가 지금 실패하는지 확인한다. 실패하지 않으면 지금 동작을 겨눈 초안이다
- AI에게 주는 지시:
  - 작성 후 `test-guide.md` 가이드라인 준수 여부를 확인하고, 새로 정한 규칙은 `test-guide.md`에 추가할지 질문한다.
  - acceptance-criteria.md에 정식 요구사항으로 없는 내용은 테스트에 넣지 않는다. 넣고 싶으면 먼저 acceptance-criteria.md에 요구사항으로 추가하거나 티켓으로 등록한다.

## 3. 구현

- 입력: 실패하는 인수 테스트
- 하는 일: 그 테스트를 통과시키는 최소 변경
- 남기는 것: 코드
- 넘어가기 전에: 실패하던 인수 테스트가 통과하는지 확인한다
- AI에게 주는 지시:
  - 기존 코드의 검증 순서(예: "값이 있는지" 먼저 → "있다면 모양이 맞는지" 그다음)를 지키며 최소로 변경한다.

## 4. 판정

- 입력: 바뀐 코드, 쌓인 테스트 전부
- 하는 일: 이 티켓이 끝났는지 판정한다. 바뀐 코드를 읽고, 쌓인 테스트를 전부 돌려 회귀를 확인한다
- 남기는 것: 커밋. 처리하며 발견한 것이 있으면 `tickets.md`에
- 넘어가기 전에: 요구사항대로 됐고 원래 되던 것이 안 깨졌는지 확인한다
- AI에게 주는 지시:
  - 판정은 새로운 subagent를 통해 진행한다.
  - 작업 중 발견한 것 중 못 정한 것은 tickets.md에 남긴다. acceptance-criteria.md에 없는 규칙을 코드에서 만나면 사양인지 버그인지 판단하지 않고 티켓으로 남긴다.
  - 전체 테스트를 재실행해 회귀를 확인한다.

## 이 저장소의 실행 방법

- 서버 기동: `./gradlew bootRun`, 8080 포트. 8080이 쓰이면 `SERVER_PORT=8081 ./gradlew bootRun`
- 테스트 실행(전체 스위트): `./gradlew test`. 결과 줄이 안 보이면 캐시다. `./gradlew test --rerun-tasks`로 다시 돌린다.
  그래도 결과를 못 읽으면 통과로 치지 않고 멈춘다(`principles.md` "확인이 안 되면 통과가 아니다")
- 테스트 실행(특정 클래스만): `./gradlew test --tests "<패키지>.<파일명>"`
  (예: `./gradlew test --tests "com.camping.admin.acceptance.ProductUpdateAcceptanceTest"`). 결과
  줄이 안 보이면 마찬가지로 `--rerun-tasks`를 붙인다
- 데이터를 다루기 전에 `src/main/resources/data.sql`을 읽는다

테스트를 어떻게 짤지는 이 파일에 적지 않는다. 무엇을 단언하고 어떻게 격리할지는
작업하며 정해 `test-guide.md`에 쌓는다.

## 새 티켓 남기기

어느 단계에서든 지금 다루는 티켓 범위 밖의 문제를 발견하거나, 요구사항 자체가 침묵하는
정책(예: 유일성 제약처럼 누구도 정한 적 없는 규칙)을 만나면 스스로 판단하지 않고
`docs/tickets.md`에 아래 형식으로 남긴다.

```markdown
T-<n> <제목>

내용: T-<원본 티켓> 작업 중 확인. <발견 경위와 관련 코드 file:line 인용>
<무엇이 애매한지>는 요구사항이 침묵하므로 이 티켓에서는 판단하지 않는다.

필요: <이 티켓이 착수 가능해지려면 무엇이 정해지거나 확인돼야 하는지 — 정책 결정(예: 검증
      정책을 정한다), 사실 확인(예: 실제 운영 데이터에서 재현되는지 본다), 선행 작업(예: 없는
      API를 먼저 추가한다) 중 어느 쪽인지 구체적으로 적는다. 결정과 확인이 둘 다 필요하면
      둘 다 적는다.>

---
```

- 번호는 `docs/tickets.md`에서 가장 큰 `T-n`의 다음 번호를 쓴다. 겹치지 않는지 확인한다.
- `필요:` 줄은 착수를 막는 결정·확인·선행 작업이 실제로 있을 때만 적는다 — 이미 그 자체로
  착수 가능한 티켓(예: 원인과 고칠 방향이 분명한 버그)이면 생략한다. 있는데도 생략하면
  나중에 이 티켓을 집어들 때 코드를 다시 읽어야 착수 가능 여부를 알 수 있으니, 있으면 반드시
  적는다.
- 각 항목은 `---`로 구분한다.
- 1단계(`acceptance-criteria.md`)에서 남기는 경우, 관련 규칙 블록에도 `질문` 줄로 같은 내용을
  요약해 남긴다(`acceptance-criteria` 스킬 5단계 형식).

## AI에게 주는 지시 칸

단계마다 마지막 줄이 비어 있다. 그 단계에서 AI에게 실제로 준 지시 중 다시 쓸 만한
것을 적는 자리다. 프롬프트 전문을 옮기지 않고, 다음에도 그대로 쓸 문장만 남긴다.

두 번째 티켓에서 같은 지시를 또 하게 되면 그것이 굳힐 자리다. 네 칸에 쌓인 것이
스킬을 만들 때의 재료가 된다.
