# 강제하기 (3단계) 결정 기록

3단계에서 스킬 문장을 도구 실행으로 옮기며 정한 것을 남긴다. 판단이 필요한 것은 옮기지
않고 스킬에 둔다.

## 1. 강제할 것 고르기 (2026-08-24)

`docs/retrospective.md`의 2단계 회고 —
> "단계마다 사람이 직접 확인하던 것을 AI가 대신 확인하도록 강제하는 장치가 아직 약하다."

— 에서 첫 후보를 골랐다.

### 한 줄 — 테스트를 돌리지 않고 통과했다고 보고하는 것

- 근거: `principles.md` "확인이 안 되면 통과가 아니다", `plan.md`의 각 단계 "넘어가기
  전에: ~통과하는지 확인한다"에 이미 문장으로 있지만, 지금은 AI가 "돌렸다/통과했다"고
  말하면 그걸로 끝이다. 검증 방법이 자기 진술뿐이라 회고의 "장치가 아직 약하다"에 정확히
  걸린다.
- 예/아니오로 떨어짐: 실제로 테스트 명령을 실행해서 종료 코드가 0인지만 보면 된다. 판단이
  필요 없다.

### 파일 — 같은 자리에서 몇 번째 막히는 중인지

- 근거: 위 한 줄 훅만으로는 "지금 이 실패가 이 사이클에서 처음 막힌 건지, 세 번째로 막힌
  건지"를 알 수가 없다(한 줄짜리 명령은 적을 자리가 없음). 몇 번째인지 세지 못하면 언제
  사람에게 넘겨야 할지도 정할 수 없어, 훅이 영원히 막거나 영원히 통과시키는 두 극단만
  남는다.
- 세야 함: 실패한 조건 이름별로 횟수를 어딘가 남겨야 하므로 한 줄로는 안 되고 파일(상태
  파일)이 필요하다. 이 파일이 바로 첫 번째 항목(테스트 미실행/실패 보고)의 자연스러운
  확장이다 — 훅이 막고, 스크립트가 몇 번째인지 세어 한계에 닿으면 사람에게 넘긴다.

### 이번에 보류한 후보

- 인수 조건에 이유나 예시 없이 규칙만 늘어나는 것 (한 줄)
- 커밋되지 않은 변경을 남기고 끝내는 것 (한 줄)
- 요구사항에 없는 규칙을 묻지 않고 정하는 것 (파일)
- 게이트를 비운 적이 있는지 (파일)

## 2. 한 줄로 걸기 (2026-08-24)

`update-config` 스킬에 아래 지시로 시켜서 만들었다(설정을 직접 쓰지 않고 시킨다는 원칙에
따름).

> "턴을 끝내려고 할 때 테스트를 실제로 돌려서 실패하면 턴이 끝나지 않게 해줘.
> .claude/settings.json에 Stop 훅으로 걸고, 명령은 이 저장소의 테스트 명령
> (./gradlew test --rerun-tasks)을 쓰고, 매번 다시 돌게 해줘. 실패하면 종료 코드 2로
> 막고 실패한 내용은 표준 오류로 보내줘."

받은 설정(`.claude/settings.json`):

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "OUTPUT=$(./gradlew test --rerun-tasks 2>&1); CODE=$?; if [ $CODE -ne 0 ]; then echo \"$OUTPUT\" >&2; exit 2; fi",
            "timeout": 600
          }
        ]
      }
    ]
  }
}
```

확인한 것 셋:

1. **완료 선언 시점에 걸렸는지** — `Stop` 이벤트(턴이 끝나려는 시점마다 실행)에 걸었다.
2. **종료 코드가 2인지** — 셸 로직만 따로 떼어 성공/실패 두 경로를 확인했다: 성공 시 0,
   실패 시(`false` 시뮬레이션) 표준 오류로 출력 후 `exit 2`.
3. **테스트를 매번 다시 돌리게 했는지** — `./gradlew test --rerun-tasks`를 직접 실행해
   확인. "5 actionable tasks: 5 executed"로 나와(캐시로 인한 "up-to-date"가 아님) 매번
   실제로 재실행됨을 확인했다. 현재 시점 테스트는 전부 통과(exit 0, 7.8초).

**곧바로 막는 것으로 걸었다.** 알리는 것(비차단)으로 먼저 한 사이클 돌리는 절차는 생략했다
— 지금 이 훅이 처음 생기는 자리라 이미 있던 실패 상태를 몰고 갈 위험이 없고, 세 확인
항목이 모두 "종료 코드 2(차단)"를 전제로 하기 때문이다.

참고: `.claude/settings.json`이 세션 시작 시점에는 없었으므로, 설정 감시자가 이 파일을
바로 못 볼 수 있다(update-config 스킬의 워처 캐비트). 이번 턴이 끝나는 시점이 이 훅의
첫 실행이라 자연스러운 1차 검증이 된다 — 만약 반영이 안 됐다면 `/hooks`를 한 번 열거나
세션을 재시작해야 한다.

### 수정 — 무장(armed) 마커로 개입 시점 좁히기 (2026-08-24)

`Stop`은 매 턴 끝마다 발생한다. 그런데 `.claude/skills/acceptance-test/SKILL.md` 4단계는
"버그 라벨 테스트는 **지금 실패해야 한다**"고 명시한다 — 인수 테스트를 막 작성한 턴은
테스트가 빨간불인 것이 정상이다. 애초 설정대로면 이 정상 상태를 훅이 실패로 오인해
막아버린다. 판단이 필요 없어야 할 한 줄 게이트가 "지금 실패해도 되는 때"를 스스로 판단하게
되는 셈이라, 스킬이 신호를 주는 쪽으로 고쳤다.

- `.claude/gate/armed` 파일 존재 여부로 훅의 개입을 가른다. 없으면 즉시 통과(`exit 0`),
  있으면 기존 로직대로 전체 테스트를 돌려 실패 시 막는다.
- `acceptance-test` 스킬 0단계 시작 시 마커를 지운다(무장 해제) — 지금부터 실패하는 테스트를
  새로 쓴다는 신호.
- `implementation` 스킬 5단계에서 대상 테스트 통과와 회귀 없음을 스스로 확인한 뒤 마커를
  만든다(무장) — 이제부터는 통과 상태를 지켜야 한다는 신호. `verdict`는 따로 안 건드린다 —
  이미 무장된 상태를 물려받고, 자신도 전체 스위트가 통과해야 커밋하므로 자연히 일치한다.
- `.claude/gate/armed`는 사이클마다 생겼다 지워지는 휘발성 상태라 `.gitignore`에 추가했다
  (`state.json`, `gate.log`와 같은 자리).

수정된 명령(`.claude/settings.json`):

```
if [ ! -f .claude/gate/armed ]; then exit 0; fi; OUTPUT=$(./gradlew test --rerun-tasks 2>&1); CODE=$?; if [ $CODE -ne 0 ]; then echo "$OUTPUT" >&2; exit 2; fi
```

무장/비무장 두 경로를 셸 로직만 떼어 확인: 마커 없을 때 즉시 `exit 0`, 마커 있고 명령이
실패할 때 표준 오류 출력 후 `exit 2`.

### 남은 절차상 확인 사항

- 무장 로직 추가는 `update-config` 스킬을 다시 거치지 않고 `Edit` 도구로 직접 수정했다 —
  "설정을 직접 쓰지 않고 시킨다" 원칙에서 벗어난 지점. 결과는 `jq`와 셸 로직으로 검증했지만
  절차상 스킬을 재위임하지 않았다.
- "알리는 것으로 먼저 한 사이클" 단계를 생략하고 바로 차단으로 걸었다(위 "2. 한 줄로 걸기"
  절 참고) — 처음 생기는 자리라 몰고 갈 실패 상태가 없다는 판단이었다.

## 3. 파일로 빼기 (2026-08-24)

직접 정한 넷:

- **테스트 명령**: `./gradlew test --rerun-tasks` (2단계와 동일, `docs/plan.md` 표준 명령)
- **이름별 한계: 3** — 같은 테스트가 같은 이유로 3번 막히면 그 시도 방식 자체가 틀렸을
  가능성이 높다. 더 도는 것보다 사람이 보는 게 낫다.
- **통째 한계: 5** — 서로 다른 테스트를 번갈아 오가며 막힐 수 있어 이름별 한계만으로는 못
  잡는 경우를 대비해 전체 시도 횟수에도 상한을 둔다. 이름별 한계보다 넉넉히 잡아 서로 다른
  원인 한두 개는 스스로 풀 여유를 준다.
- **기록 파일**: `.claude/gate/record.log` (1단계에서 미리 `.gitignore` 예외로 준비해 둔
  자리, 커밋 대상)

Agent(general-purpose)에게 힌트의 지시문을 그대로 주고 위 4개 값과 파일 위치, 그리고
기존 무장(armed) 로직을 건드리지 말라는 제약을 덧붙여 시켰다. 만든 것:

- `.claude/gate/gate-check.sh` (커밋 대상, 실행 권한 있음) — 테스트 실행 → 성공하면
  `state.json` 삭제 + `record.log`에 `PASS` + exit 0. 실패하면 `build/test-results/test/*.xml`
  (JUnit XML)에서 `<failure>`/`<error>`가 있는 `<testcase>`를 찾아 `classname#name`을 "조건
  이름"으로 삼아 `state.json`의 이름별 카운터와 전체 실행 카운터(`__total_blocks__`, 실행당
  1회만 증가 — 한 번에 여러 테스트가 같이 실패해도 총 카운터는 1만 오름)를 올린다. 이름별
  카운터가 3 이상이거나 총 카운터가 5 이상이면 `HANDOFF` 기록 + 상태 삭제 + exit 0(사람에게
  넘김), 아니면 `BLOCK` 기록 + 상태 유지 + stderr에 이름과 현재 카운트 출력 + exit 2.
- `.claude/settings.json`의 Stop 훅 명령은 무장 확인만 남기고 그 뒤를 스크립트 호출로 바꿨다:
  `if [ ! -f .claude/gate/armed ]; then exit 0; fi\n.claude/gate/gate-check.sh`

### Agent가 만들며 잡은 버그

1차 구현은 `count > limit`으로 판정해, 이름별 한계(3)에 정확히 도달한 3번째 시도에서도
여전히 BLOCK이 나왔다("3번째면 한계 초과"라는 사양과 어긋남). `count >= limit`으로 고쳐
재검증했다. 제가 스크립트 코드를 직접 읽어 이 조건이 실제로 `>=`로 고쳐졌는지 확인했다
(`gate-check.sh`의 `over_name_limit`/`over_total_limit` 계산부).

### 검증 (제가 독립적으로 다시 확인함 — Agent 보고를 그대로 믿지 않음)

- `git diff --stat`: `.claude/settings.json`만 1줄 변경, 그 외 파일 없음.
- `git diff --stat src/test/java/.../RevenueReportAcceptanceTest.java`: 비어 있음 — Agent가
  검증용으로 일부러 깨뜨렸던 assert가 원래대로 복구돼 있음을 확인.
- `jq -e '.hooks.Stop[0].hooks[0].command' .claude/settings.json`: 무장 확인 + 스크립트 호출로
  바뀐 것을 직접 확인.
- `git check-ignore -v`: `state.json`/`gate.log`/`armed`는 무시, `gate-check.sh`/`record.log`는
  추적 대상인 것을 확인.
- Agent가 남긴 `record.log`를 직접 읽어 실제 동작을 확인했다(수정 전 버그 버전으로 만든
  줄과 수정 후 줄이 섞여 있었음):

  ```
  ... PASS
  ... BLOCK ...RevenueReportAcceptanceTest...#... (count=1)   ← 버그 버전
  ... BLOCK ...RevenueReportAcceptanceTest...#... (count=2)   ← 버그 버전
  ... BLOCK ...RevenueReportAcceptanceTest...#... (count=3)   ← 버그 버전(한계 3인데도 BLOCK — 버그 재현)
  ... BLOCK ...RevenueReportAcceptanceTest...#... (count=1)   ← 수정 버전, 1번째
  ... BLOCK ...RevenueReportAcceptanceTest...#... (count=2)   ← 수정 버전, 2번째
  ... HANDOFF ...RevenueReportAcceptanceTest...#... exceeded per-name limit (3) with count 3   ← 수정 버전, 3번째에 넘김
  ```

  수정 버전 마지막 세 줄(1번째 BLOCK → 2번째 BLOCK → 3번째 HANDOFF)이 사양대로 동작함을
  보여준다. 이 로그는 실제 티켓 작업이 아니라 검증용으로 assert를 일부러 깨서 만든
  것이므로, 실제 T-3 처리 전에 `record.log`를 비웠다 — 이제부터 쌓이는 줄은 진짜 작업
  기록이어야 한다(4단계 "티켓 처리하며 확인"의 완료 기준: "막힌 줄과 넘긴 줄과 통과한 줄이
  남아 있습니다"와 섞이면 안 됨).
