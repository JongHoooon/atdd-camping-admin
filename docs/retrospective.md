- 절차를 알아서 빨라진 것: 인수 조건과 인수 테스트를 작성하는 절차와 포맷을 미리 정해둬서 작성이 빨라졌다.
- 이번에 덜 판 것: 단계마다 사람이 직접 확인하던 것을 AI가 대신 확인하도록 강제하는 장치가 아직 약하다.
- 손으로 반복한 것 중 다음 저장소에서도 또 할 것 같은 것: acceptance-criteria 작성 후 회색 지대(판단 기준이 애매하게 남은 지점)가 없는지 서브에이전트 기반으로 한 번 더 확인하게 한다.
  - 무엇을 겪어서였는지:  AI가 작업하면서 항상 회색 지대를 확인하지는 않는다고 느껴 명시적으로 작성했습니다. 그리고 "만드는 쪽과 판정하는 쪽의 분리"하는 이유로 서브에이전트를 통해 더 객관 적으로 회색지대를 확인하도록했습니다.
- T-1, T-2 AI 판정 보고와 직접 실행한 결과가 일치한다.

## step3
- 스킬에 무엇을 검증으로 적었나: 4개 스킬(acceptance-criteria/acceptance-test/implementation/verdict) 모두에 "멈추는 조건"(회색지대/맴돌다 끊김/예산 소진 자기판단)과, 0단계에서 `.claude/gate/state.json`에 실행 중인 스킬·완료 여부·테스트 실행 여부를 스스로 적어두는 자기보고를 넣었다.
- 무엇을 겪어서 스킬에 무엇을 더했나: `acceptance-criteria` 스킬을 실행할 때마다 완료 직전 회색지대 점검을 매번 반복해, 스킬 7단계(완료 기준)에 서브에이전트가 회색지대를 점검하는 절차를 더했다.
- AI가 멈춘 자리에서 무엇을 판정했나: 판단이 필요한 지점을 만나면 먼저 이번 티켓 범위 안의 문제인지부터 판정했다 — 범위 밖이면 새 티켓으로 분리하고, 범위 안이면 문제 상황을 회색지대/맴돌다 끊김/예산 소진 3가지로 분류해 그에 맞게 처리했다.
- 절차를 알아서 빨라진 것과 이번에 덜 판 것: 4단계 스킬을 실행하는 동안 사람이 개입할 일이 줄어 전체 진행이 빨라졌다. 하지만 훅, 스크립트로 코드에 박아 넣은 부분과 달리, 스킬 문서에 "이 명령을 실행하라"고만 적어 둔 부분은 AI가 실제로 따르는지 보장할 방법이 없다. 이 부분을 덜 팠다고 생각한다.
