# T-1 인수 조건

"관리자 화면에서 상품 재고를 수정했는데, 저장했다고 나오고선 값이 그대로입니다."

요구사항: 상품 정보를 수정하면 그 값이 저장되어야 합니다.

```
규칙   상품 정보를 수정하면(이름·재고·가격·유형 중 무엇을 바꾸든) 그 값이 저장되어야 한다.
이유   재고·가격은 판매/대여 가능 여부와 결제 금액 산정의 기준이라, 저장되지 않으면 실제와
       다른 값으로 처리된다.

Given  테스트랜턴 상품(name=테스트랜턴, stockQuantity=20, price=30000, productType=RENTAL)
When   재고를 99로 수정         Then  응답엔 반영되나 재조회 시 (버그) 재고 20(그대로) → 기대 99
When   이름을 "새랜턴"으로 수정   Then  응답엔 반영되나 재조회 시 (버그) 이름 "테스트랜턴"(그대로) → 기대 "새랜턴"
When   가격을 45000으로 수정     Then  응답엔 반영되나 재조회 시 (버그) 가격 30000(그대로) → 기대 45000
When   유형을 SALE로 수정       Then  응답엔 반영되나 재조회 시 (버그) 유형 RENTAL(그대로) → 기대 SALE

질문   음수 재고/가격, 빈 이름, 파싱 불가능한 값(문자열 stockQuantity, 정의되지 않은 productType)을
       어떻게 처리해야 하는지 요구사항이 침묵한다.
       → 실측 결과 숫자 필드는 검증 없이 그대로 반영되고(음수도 허용), 빈 문자열 이름도 그대로
       반영되며, 파싱 불가능한 값은 에러 없이 조용히 무시되고 해당 필드만 안 바뀐다(모두 200).
       "수정하면 저장되어야 한다"는 이 티켓의 요구사항은 값 검증 정책을 다루지 않으므로 T-1
       범위에서는 판단하지 않는다. T-5로 분리.
```

```
규칙   상품 정보 중 일부만 수정하면, 요청에 없는 필드(예: 재고, 가격)는 원래 값 그대로
       유지되어야 한다.
이유   저장 버그(위 규칙)를 고치는 과정에서 이 부분 수정 로직이 함께 깨지지 않도록 지금
       동작을 회귀 방지 조건으로 고정해 둔다.

Given  새로 등록한 상품(name=테스트랜턴, stockQuantity=20, price=30000, productType=RENTAL)
When   name만 "새랜턴"으로 수정   Then  응답의 stockQuantity=20, price=30000.00, productType=RENTAL — 요청에 없던 필드는 그대로 (정상, 회귀 방지)
```

# T-2 인수 조건

"매출 리포트 금액이 화면마다 다르게 나옵니다."

요구사항: 같은 거래는 어느 리포트에서 보든 같은 날, 같은 금액으로 잡혀야 합니다.

```
규칙   대여(rental) 거래의 매출 금액은 조회 시점의 상품 가격이 아니라 거래가 발생한
       시점의 금액으로 고정되어야 한다.
이유   그렇지 않으면 상품 가격이 바뀔 때마다 이미 끝난 같은 대여 거래의 매출이 리포트를
       다시 열어볼 때마다 달라져 "같은 거래는 같은 금액으로 잡혀야 한다"는 요구사항을
       어긴다. 대여 매출은 조회 시점에 상품의 현재 가격을 다시 곱해 계산한다
       (service/SalesService.java 세 리포트 메서드 모두 rr.getProduct().getPrice() 사용).

Given  랜턴 상품(id=1, 당시 가격 30000원)으로 워크인 대여 생성(T-9 PK 충돌 재시도로 3건 생성됨, 조건 동일)
When   가격 변경 전 오늘자 매출 상세내역 조회        Then  대여 항목 금액 30000원 (정상)
When   상품 가격을 99000원으로 변경 후 같은 기간 재조회   Then  (버그) 같은 대여 거래의 금액이 99000원으로 바뀜 → 기대 거래 시점 금액 30000원 유지
When   가격 변경 전 오늘자 일별 리포트(daily)의 totalRentalRevenue 조회      Then  이 대여 거래만큼(30000원) 반영 (정상)
When   상품 가격을 99000원으로 변경 후 같은 날짜로 일별 리포트 재조회        Then  (버그) 같은 대여 거래의 반영분이 99000원으로 바뀜 → 기대 거래 시점 금액 30000원 유지
When   가격 변경 전 오늘자 기간 리포트(range)의 totalRentalRevenue 조회      Then  이 대여 거래만큼(30000원) 반영 (정상)
When   상품 가격을 99000원으로 변경 후 같은 기간으로 기간 리포트 재조회       Then  (버그) 같은 대여 거래의 반영분이 99000원으로 바뀜 → 기대 거래 시점 금액 30000원 유지

질문   "어느 리포트에서 보든"이라는 요구사항 문구는 문자 그대로는 같은 시점 화면 간 비교로
       읽히는데, 이 규칙이 잡은 버그는 같은 화면을 가격 변경 전/후 두 시점에 재조회했을 때
       달라지는 문제라 시간축 문제에 가깝다(실제로 규칙 3에서 확인했듯 같은 시점엔 세 화면이
       항상 서로 일치한다 — 셋 다 같은 방식으로 잘못 계산할 뿐). 사용자 확인 결과 "같은
       거래는 같은 금액"을 시점과 무관한 데이터 무결성 요구로 넓게 해석해 T-2 범위에 유지하기로
       했다(2026-08-23 확인).
```

```
규칙   판매(sales) 거래의 매출 금액은 이후 상품 가격이 바뀌어도 거래 시점 금액 그대로
       유지되어야 한다.
이유   대여와 달리 판매는 거래 시점에 계산한 금액을 SalesRecord.totalPrice로 저장해 두므로

When   판매 전(baseline) 대비 판매 직후/가격 변경 후 일별 리포트(daily)의 totalSalesRevenue 증가분을 각각 확인   Then  두 시점 모두 55555원 증가로 동일 (정상, 회귀 방지)
When   판매 전(baseline) 대비 판매 직후/가격 변경 후 기간 리포트(range)의 totalSalesRevenue 증가분을 각각 확인   Then  두 시점 모두 55555원 증가로 동일 (정상, 회귀 방지)
```

```
규칙   같은 시점에 조회하면 일별 리포트·기간 리포트·기간 상세내역의 합계 금액이 서로

이유   세 화면이 같은 거래 데이터를 서로 다른 집계 단위로 보여줄 뿐이므로, 그중 하나만
```

# T-3 인수 조건

"예약을 취소 처리했는데 그날 매출이 안 줄어듭니다."

요구사항: 취소된 예약은 매출에 포함되지 않아야 합니다.

```
규칙   예약 상태가 취소이면 일별 리포트·기간 리포트·기간 상세내역 어디에서도 그 예약의
       매출이 집계되지 않아야 한다.
이유   취소된 예약이 매출로 남으면 실제보다 부풀려진 금액을 기준으로 정산·통계가 이뤄져
       운영 판단을 그르친다(service/SalesService.java 세 리포트 메서드 모두 해당).

Given  예약 생성 API가 없어(관리자용 시스템이라 예약은 조회·상태변경만 제공) data.sql
       시드 예약 #1(오늘 reservationDate, 1박, 매출 50000원)과 #2(오늘 reservationDate,
       1박, 매출 50000원)를 그대로 썼다 — 상태만 PATCH로 바꿔가며 관찰했다. 오늘(2026-08-25)
       기준 취소 전 두 예약 모두 CONFIRMED, 오늘자 예약 매출 합계 100000원(1건당 50000원).
When   예약 #2 상태를 CANCELLED로 변경 후 같은 날짜로 일별 리포트(daily) 재조회   Then  (버그) totalReservationRevenue 100000원 그대로 → 기대 50000원(취소분 제외)
When   같은 상태 변경 후 같은 날짜 범위로 기간 리포트(range) 재조회              Then  (버그) totalReservationRevenue 100000원 그대로 → 기대 50000원
When   같은 상태 변경 후 같은 범위로 기간 상세내역(entries) 재조회               Then  (버그) 예약 #2 항목이 그대로 남음 → 기대 목록에서 제외

질문   취소 말고 다른 상태(WAITING/PENDING/REJECTED/CHECKED_IN/CHECKED_OUT)를 매출 집계에서
       어떻게 다뤄야 하는지는 이 티켓이 다룰 요구사항에서 "확인하며 판정한다"고 이미 범위를
       좁혀 뒀다. 실측 결과 현재는 이 다섯 상태 모두 취소와 마찬가지로 상태와 무관하게 전부
       매출에 포함된다(위와 같은 방식으로 반복 실측). 어떤 상태를 포함/제외해야 하는지는
       요구사항이 침묵하므로 이 티켓에서는 판단하지 않는다. T-11로 분리.
```

# T-5 인수 조건

"상품 수정 시 값 검증 정책이 없음" — 음수 재고/가격, 빈 이름, 파싱 불가능한 값이 검증 없이
그대로 저장된다.

요구사항: 상품 정보를 수정할 때 요청에 포함된 필드 값이 유효하지 않으면(음수 재고, 음수 가격,
빈 문자열 이름, 정의되지 않은 productType, 숫자로 파싱할 수 없는 재고/가격) 어떤 필드도
반영하지 않고 400 Bad Request와 거부 사유를 알 수 있는 메시지를 반환해야 한다. 요청에 없는
필드는 기존 정책대로 그대로 유지한다(T-1 회귀 방지 규칙과 동일).

```
규칙   상품 정보를 수정할 때 요청에 포함된 값이 무효(음수 재고, 음수 가격, 빈 문자열 이름,
       정의되지 않은 유형, 숫자로 파싱할 수 없는 값)이면 그 필드를 반영하지 않고 400 Bad
       Request와 거부 사유를 알 수 있는 메시지를 반환해야 한다.
이유   재고·가격은 판매/대여 가능 여부와 결제 금액 산정의 기준이라, 무효한 값이 그대로
       저장되면 실제와 다른 값으로 처리된다. 지금은 값 검증이 전혀 없다
       (controller/ProductAdminController.java:106-154).
```
